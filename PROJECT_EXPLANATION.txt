2. DATABASE (model_store.sql)
---------------------------------------------------------------------------
Five tables:

  users
    id, full_name, email (unique), password (bcrypt hash), role
    (enum 'user' / 'admin', default 'user'), created_at

  categories
    id, name, slug (unique)  e.g. Hypercars / supercars

  products
    id, category_id (FK -> categories), title, description, price,
    stock, scale (1:18 / 1:43 / 1:64), type (Diecast / Resin),
    image_url (local path or external URL), created_at

  orders
    id, user_id (FK -> users, nullable), full_name, phone, address, city,
    total_amount, payment_method ('esewa' / 'cod'),
    payment_status (enum pending/completed/failed),
    status (enum Pending/Processing/Shipped/Completed/Cancelled),
    transaction_uuid (unique), esewa_ref_id, created_at

  order_items
    id, order_id (FK -> orders, cascade delete), product_id (FK -> products),
    quantity, unit_price

---------------------------------------------------------------------------
3. HOW THE DATABASE CONNECTION IS DONE (config/db.php)
--------------------------------------------------------------------------
The entire site connects to MySQL through ONE shared file: config/db.php.
Every page includes it at the very top, and because the file is included
exactly once per request, a single $pdo connection object is shared by all
queries on that page.

3.1 What db.php does, line by line
  1. Starts a session if none is active:
       if (session_status() === PHP_SESSION_NONE) session_start();
     This makes $_SESSION available on every page without adding a separate
     session_start() call everywhere.

  2. Defines the connection credentials:
       $host     = 'localhost';
       $dbname   = 'model_store';
       $username = 'root';
       $password = '';            // XAMPP default (no password)
     These match the default XAMPP MySQL setup.

  3. Builds the PDO DSN (Data Source Name) with UTF-8 encoding so Nepali
     text / special characters are stored and displayed correctly:
       $dsn = "mysql:host={$host};dbname={$dbname};charset=utf8mb4";

  4. Sets PDO options:
       PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION   -> SQL errors
                                                                   throw PDOException
       PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC         -> rows come back
                                                                   as associative
                                                                   arrays (column name => value)
       PDO::ATTR_EMULATE_PREPARES   => false                    -> use REAL server-side
                                                                   prepared statements

  5. Creates the connection:
       $pdo = new PDO($dsn, $username, $password, $options);
     If it fails, PDOException is thrown and caught, and the script dies:
       die("Database Connection Failed: ...");

  6. Defines the global money helper used everywhere:
       function format_price($amount) {
           return 'Rs. ' . number_format((float)$amount, 2);
       }
     e.g. format_price(2399)  ->  "Rs. 2,399.00"

3.2 How every page uses it
  The first line of most pages is:
      require_once 'config/db.php';
  ('require_once' - not 'include' - so the connection is created only once
  even if multiple files include it. It is fatal if the file is missing.)

  After that, $pdo is ready to use anywhere on the page. Examples:

  - A simple query (no user input, safe to run directly):
      $pdo->query("SELECT * FROM categories ORDER BY name ASC")->fetchAll();

  - A prepared query with user input (prevents SQL injection):
      $stmt = $pdo->prepare("SELECT * FROM products WHERE id = ?");
      $stmt->execute([$product_id]);
      $product = $stmt->fetch();

  - An INSERT / UPDATE with parameters:
      $stmt = $pdo->prepare("INSERT INTO users (full_name, email, password) VALUES (?, ?, ?)");
      $stmt->execute([$name, $email, $hashedPassword]);

  - Transactions (used in checkout.php so order + items + stock update are
    all-or-nothing):
      $pdo->beginTransaction();
      ... insert order, insert items, decrement stock ...
      $pdo->commit();        // or $pdo->rollBack() on error

3.3 Why prepared statements everywhere
  - Because ATTR_EMULATE_PREPARES is false, placeholders (?) are sent to
    MySQL as real parameters - the database never mixes user input into the
    SQL text, so SQL injection is impossible.
  - Binding parameters also means you never need to quote/escape values.

3.4 Result-fetching methods used in the project
  - fetch()        -> first matching row as an associative array (or false)
  - fetchAll()     -> all matching rows as an array of associative arrays
  - fetchColumn()  -> the first column of the first row (e.g. COUNT(*))
  - lastInsertId() -> the auto-increment id of the last INSERT
    (used in checkout.php to get the new order id)

3.5 How the admin pages use it
  Admin files live in the admin/ subfolder, so they include the connection
  with a relative path one level up:
      require_once '../config/db.php';

SECURITY NOTE: All SQL in the project uses PDO prepared statements
(parameterized queries), which protects against SQL injection. All user
output is escaped with htmlspecialchars(). Passwords are hashed with
password_hash() (bcrypt) and verified with password_verify().

---------------------------------------------------------------------------
4. AUTHENTICATION (login.php / register.php / logout.php)
---------------------------------------------------------------------------
Register (register.php):
  - Takes full_name, email, password via POST.
  - Sanitizes the email with FILTER_SANITIZE_EMAIL.
  - Hashes the password with password_hash($pass, PASSWORD_BCRYPT).
  - Inserts the user with role defaulting to 'user'.
  - Duplicate email -> PDOException caught -> "Email already registered".

Login (login.php):
  - Looks up the user by email, then password_verify() the submitted
    password against the stored hash.
  - On success stores in $_SESSION: user_id, full_name, role.
  - Redirects admins to admin/dashboard.php.
  - Supports a ?redirect= parameter (used by checkout.php) so a logged-out
    user is sent back to checkout after logging in. The redirect value is
    validated with a whitelist regex to avoid open-redirect attacks.

Logout (logout.php):
  - Clears $_SESSION, expires the session cookie, calls session_destroy(),
    redirects to login.php.

Role check:
  - Admin pages verify:  $_SESSION['role'] === 'admin'
    (note: add-product.php uses $_SESSION['user_role'] which is a bug -
    it never matches, so that page is effectively always blocked;
    products.php is the page actually used for management).

---------------------------------------------------------------------------
5. CATALOG & PRODUCT PAGES (index.php / product.php)
---------------------------------------------------------------------------
index.php (catalog):
  - Reads GET params: q (search), scale, category, page (pagination).
  - Builds a dynamic SQL query "FROM products ... LEFT JOIN categories
    ... WHERE 1=1" and appends conditions:
      * q      -> title LIKE ? OR description LIKE ?  (with % wildcards)
      * scale  -> p.scale = ?
      * category -> c.slug = ?
  - Runs a COUNT(*) version to compute total pages, then a LIMIT/OFFSET
    version to fetch just the current page (6 products per page).
  - Renders product cards: image, scale badge, category label, title,
    price (format_price), and an "Add to Cart" form that POSTs to cart.php
    with data-ajax-add (handled by app.js for AJAX).
  - Includes pagination links that preserve search/filter query strings.

product.php (detail):
  - Validates the ?id GET parameter.
  - SELECTs the product joined with its category name.
  - Shows image, title, scale, type, price, description, stock status.
  - "Add to Cart" -> POST to cart.php; "Buy Now" -> GET to
    checkout.php?id=... (single-product direct checkout).

---------------------------------------------------------------------------
6. SHOPPING CART (cart.php)
---------------------------------------------------------------------------
The cart lives in the PHP session: $_SESSION['cart'] is an associative
array keyed by product_id.

Actions (handled by POST with an 'action' field):
  add:
    - Validates product_id/quantity, re-reads the product from the DB to
      get fresh price/title/image/category.
    - If the item already exists in the cart it increments quantity;
      otherwise it adds a new entry with all product details.
    - If the request is AJAX (HTTP_X_REQUESTED_WITH = XMLHttpRequest) it
      returns JSON { success, cart_count }; otherwise it redirects.
  update:
    - Sets the quantity for an existing product_id (min 1).
  remove:
    - unsets the product_id from the cart.

Page display:
  - Computes grand_total (price x quantity summed) and total_items.
  - Renders each cart row with a quantity stepper + update form, subtotal,
    and remove button.
  - Order summary sidebar shows subtotal, "Free" shipping, grand total.
  - "Proceed to Checkout" submits a GET form to checkout.php?id=<first item>.

Header cart badge: header.php sums the cart quantities and shows a badge.

---------------------------------------------------------------------------
7. CHECKOUT & ORDER CREATION (checkout.php)
---------------------------------------------------------------------------
- Requires the user to be logged in; if not, redirects to
  login.php?redirect=checkout.php... (so they return after login).
- Builds the list of items to buy:
    * If ?id (or product_id) is set -> single-product direct checkout
      (fetches the product from the DB, quantity 1).
    * Otherwise -> uses every item in the session cart.
  grand_total is accumulated as price x quantity.
- Form fields: full_name, phone, city, address, and a radio for payment
  method: 'esewa' (default) or 'cod' (Cash on Delivery).
- On "Place Order" (POST):
    1. Validates required shipping fields.
    2. beginTransaction().
    3. INSERTs the order into orders with payment_status 'pending',
       status 'Pending'.
    4. Creates transaction_uuid = "ORD-{order_id}-{time()}" and stores it.
    5. INSERTs one row per item into order_items.
    6. commit(); then unsets the session cart.
    7. Routes based on payment method:
         * eSewa -> builds signature and renders an auto-submitting HTML
           form that POSTs to the eSewa payment URL (see section 8).
         * cod   -> redirects to order-success.php?transaction_uuid=...&status=cod
    8. On any exception: rollBack() and show the error.

NOTE on DB integrity: checkout.php does NOT decrement product stock when an
order is placed.

8. ESEWA PAYMENT INTEGRATION  (IMPORTANT)
---------------------------------------------------------------------------
eSewa is a popular Nepali digital wallet. This project uses eSewa v2.0 in
SANDBOX (test) mode.

Sandbox credentials used (config/esewa.php + hardcoded in checkout.php):
  Merchant/Product code : EPAYTEST
  Secret key            : 8gBm/:&EnhH.1/q
  Payment URL (form)    : https://rc-epay.esewa.com.np/api/epay/main/v2/form

---------------------------------------------------------------------------
8.1 Flow overview
---------------------------------------------------------------------------
  1. Customer fills shipping details in checkout.php and clicks the button.
  2. PHP creates the order in the DB (payment_status = 'pending') and
     generates a unique transaction_uuid.
  3. PHP computes an HMAC-SHA256 signature from the amount fields and
     builds a hidden HTML form that auto-submits to eSewa.
  4. Customer pays on the eSewa hosted page.
  5. eSewa redirects the browser back to:
       success_url -> order-success.php?data=...     (on success)
       failure_url -> failure.php?data=...           (on failure/cancel)
  6. order-success.php decodes the returned 'data' (base64 JSON), rebuilds
     the signature from the returned fields and compares it to the returned
     'signature'. If they match, the payment is genuine and the order is
     marked completed. If not, it refuses to mark the order paid
     (signature mismatch).
  7. failure.php marks the order payment_status = 'failed'.

---------------------------------------------------------------------------
8.2 Generating the signature (outgoing request)
---------------------------------------------------------------------------
In checkout.php the following happens for eSewa payments:

  $amount                  = (string)$grand_total;   // the actual total
  $tax_amount              = "0";
  $product_service_charge  = "0";
  $product_delivery_charge = "0";
  $total_amount = amount + tax + service charge + delivery charge;

  $product_code = "EPAYTEST";
  $secret_key   = "8gBm/:&EnhH.1/q";

  // eSewa requires the fields in THIS exact order:
  $data_to_hash = "total_amount={$total_amount},transaction_uuid={$transaction_uuid},product_code={$product_code}";

  $raw_hash  = hash_hmac('sha256', $data_to_hash, $secret_key, true);
  $signature = base64_encode($raw_hash);

A hidden form is then rendered that POSTs to the eSewa sandbox URL with:
  amount, tax_amount, total_amount, transaction_uuid, product_code,
  product_service_charge, product_delivery_charge,
  success_url (http://localhost/model_store/order-success.php),
  failure_url (http://localhost/model_store/failure.php),
  signed_field_names = "total_amount,transaction_uuid,product_code",
  signature (the base64 HMAC above)

The page shows a spinner and auto-submits on window.onload.

There is also a helper function in config/esewa.php,
generate_esewa_signature($total_amount, $transaction_uuid, $product_code),
which does the exact same HMAC calculation. NOTE: checkout.php does the
computation inline instead of calling this helper, so if you change the
secret key you must change it in BOTH places.

---------------------------------------------------------------------------
8.3 Verifying the callback (order-success.php)
---------------------------------------------------------------------------
eSewa returns the result in a query parameter named 'data' containing
base64-encoded JSON, e.g.:
  data = base64_encode(json_encode({
    status, transaction_code, total_amount, transaction_uuid,
    product_code, signed_field_names, signature, ...
  }))

order-success.php:
  1. base64_decode('data') -> json_decode -> $response.
  2. Only continues if $response['status'] === 'COMPLETE'.
  3. Rebuilds the signed payload string from signed_field_names:
       foreach (explode(',', signed_field_names) as $field)
         payload .= "field=value,"
     This is the same "field=value" format used when generating.
  4. Computes hash_hmac('sha256', payload, secret_key) -> base64 and
     compares with $response['signature'].
  5. If signatures match:
       - Looks up the order by transaction_uuid.
       - Updates orders SET payment_status = 'completed',
         status = 'Processing', esewa_ref_id = transaction_code.
  6. Shows a success page with order details and purchased items.

If the signature does NOT match, the page shows "Security check failed:
Signature mismatch detected." and does NOT update the order - this prevents
anyone from faking a successful payment by just visiting the URL.

---------------------------------------------------------------------------
8.4 success.php and failure.php (older/duplicate pages)
---------------------------------------------------------------------------
config/esewa.php still points ESEWA_SUCCESS_URL / ESEWA_FAILURE_URL at
http://localhost/success.php and http://localhost/failure.php (root of
localhost), but checkout.php hardcodes the real URLs to
http://localhost/model_store/order-success.php and failure.php.

  success.php: A simpler handler. Decodes 'data' and, if status is
    COMPLETE, updates the order to 'completed' and stores esewa_ref_id.
    NOTE: it does NOT verify the HMAC signature, so order-success.php is
    the secure/canonical success page.
  failure.php: Decodes 'data' and, if a transaction_uuid exists, marks
    the order payment_status = 'failed'.

8.5 STEP-BY-STEP: HOW THE ESEWA INTEGRATION WAS BUILT
---------------------------------------------------------------------------
The following are the actual steps followed to add eSewa v2.0 (sandbox)
payment support to this project:

STEP 1 - Set up the sandbox credentials (config/esewa.php)
  - Registered for eSewa merchant sandbox access (UAT environment).
  - Got the test merchant/product code: EPAYTEST
  - Got the test secret key: 8gBm/:&EnhH.1/q
  - Defined the constants:
      ESEWA_MERCHANT_CODE = 'EPAYTEST'
      ESEWA_SECRET_KEY    = '8gBm/:&EnhH.1/q'
      ESEWA_PAYMENT_URL   = https://rc-epay.esewa.com.np/api/epay/main/v2/form
      ESEWA_SUCCESS_URL   = http://localhost/success.php
      ESEWA_FAILURE_URL   = http://localhost/failure.php
  - Wrote generate_esewa_signature($total_amount, $transaction_uuid,
    $product_code) helper that builds the HMAC-SHA256 signature.

STEP 2 - Add the transaction_uuid and esewa_ref_id columns to the DB
  - In model_store.sql added to the orders table:
      transaction_uuid varchar(100) UNIQUE  (unique order reference)
      esewa_ref_id     varchar(100)         (eSewa transaction reference)

STEP 3 - Generate the signature and redirect form (checkout.php)
  - When the order is placed with payment_method = 'esewa' (after the
    order + order_items are inserted and the transaction commits), build
    the payment request:
      1. Set amount = grand_total, tax/service/delivery charges = 0,
         total_amount = the sum of all of them.
      2. Create a unique transaction_uuid = "ORD-{order_id}-{time()}".
      3. Build the exact string eSewa requires, fields in this order:
           total_amount={total_amount},transaction_uuid={transaction_uuid},product_code={product_code}
      4. Sign it with HMAC-SHA256 using the secret key, then base64:
           hash_hmac('sha256', $data_to_hash, $secret_key, true) -> base64_encode()
      5. Render a hidden HTML <form> that auto-submits (on window.onload)
         to the eSewa payment URL with these fields:
           amount, tax_amount, total_amount, transaction_uuid,
           product_code, product_service_charge, product_delivery_charge,
           success_url, failure_url,
           signed_field_names = "total_amount,transaction_uuid,product_code",
           signature
  - A loading page with a spinner is shown while redirecting.

STEP 4 - Handle the success callback securely (order-success.php)
  - eSewa redirects the browser back to success_url with a 'data' query
    parameter containing base64-encoded JSON of the payment response.
  - Decode and verify:
      1. base64_decode('data') then json_decode -> $response.
      2. Check status === 'COMPLETE'.
      3. Rebuild the signed payload from the signed_field_names that eSewa
         returns (same "field=value" comma format as the request).
      4. Recompute HMAC-SHA256 + base64 and compare with the returned
         'signature'. This proves the callback really came from eSewa.
      5. If it matches, look up the order by transaction_uuid and set:
           payment_status = 'completed', status = 'Processing',
           esewa_ref_id = transaction_code
      6. Show the order confirmation with the items that were bought.

STEP 5 - Handle failure / cancellation (failure.php)
  - eSewa redirects back to failure_url with the same 'data' parameter.
  - Decode it, read transaction_uuid, and mark the order:
      payment_status = 'failed'
  - Restore the product stock that was decremented at order creation
    (quantity is added back for each order_items row).

STEP 6 - Wire it into the checkout UI (checkout.php form)
  - Added a radio group in the shipping form:
      payment_method = 'esewa' (default) or 'cod' (Cash on Delivery).
  - The POST handler branches after the order is created:
      esewa -> render the auto-submit payment form (STEP 3)
      cod   -> redirect straight to
               order-success.php?transaction_uuid=...&status=cod

STEP 7 - Verify the full flow
  - Place an order with eSewa in the sandbox, complete the fake payment,
    and confirm order-success.php shows the verified order.
  - Cancel the payment and confirm failure.php marks the order failed
    and restores the stock.

10. ADMIN PANEL (admin/)
---------------------------------------------------------------------------
Access control on every page:
  if (!isset($_SESSION['user_id']) || $_SESSION['role'] !== 'admin')
     redirect to ../login.php

dashboard.php:
  - Counts total orders, sums total_amount for non-cancelled orders
    (total revenue), counts products.
  - Lists the 5 most recent orders with customer name, total, payment
    method chip (COD / eSewa), status badge, date.

products.php (main product management):
  - ?delete=<id>   -> deletes the product.
  - ?edit=<id>     -> loads the product into the edit form.
  - POST           -> INSERT (new) or UPDATE (existing) product.
  - Image picker: scans assets/images/ for local files (glob) and lets the
    admin pick one or paste an external URL (live preview via JS).

add-product.php (legacy page):
  - Same add form plus actual file upload (move_uploaded_file to
    assets/images/ with a unique time()+uniqid() filename, only
    jpg/jpeg/png/webp allowed).
  - BUG: its access check uses $_SESSION['user_role'] which is never set
    (login.php stores 'role'), so this page always shows "Access Denied".
    Use products.php instead.

orders.php:
  - POST update_status -> updates order status only if it is one of
    Pending/Processing/Shipped/Completed/Cancelled.
  - Lists all orders joined with the customer name/email, shows payment
    method chip, payment status badge, and an inline status dropdown to
    change fulfillment status.

14. KNOWN ISSUES / THINGS TO IMPROVE
---------------------------------------------------------------------------
- Duplicate secret keys: the eSewa secret key and payment URL are
  duplicated between config/esewa.php and checkout.php (and
  order-success.php). Change them all together.
- success.php duplicates order-success.php but WITHOUT signature
  verification - keep using order-success.php.
- add-product.php is dead code (wrong session key in its access check).
- No CSRF protection on order/product/status forms.
- Checkout uses HTTP (localhost), fine for local dev.
- transactions to eSewa use string concatenation without
  number_format; ensure the amount format exactly matches what eSewa
  returns, otherwise the signature comparison will fail.
- Product stock is decremented when an order is placed (checkout.php) and
  restored on failed/cancelled eSewa payments (failure.php). Stock is NOT
  decremented again anywhere else.
