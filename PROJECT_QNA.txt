 JESTER SCALE MODELS - EXAMINER Q&A PREPARATION
============================================================================
All answers below are based on the ACTUAL code in this project. Refer to
the file paths in parentheses to back up your answers during the demo.

---------------------------------------------------------------------------
PART A - PROJECT OVERVIEW
---------------------------------------------------------------------------
Q1. What is this project?
A1. It is a fully functional e-commerce website for selling scale model
    cars. Customers can browse a catalog, search and filter products,
    add items to a cart, check out, and pay using either eSewa (Nepal's
    most popular digital wallet) or Cash on Delivery. It also has a
    customer order-history section and a complete admin panel to manage
    products and orders.

Q2. What technologies are used?
A2. Plain PHP 8.2 (no framework), MySQL/MariaDB database accessed through
    PDO, HTML, CSS, and vanilla JavaScript. It runs on the XAMPP stack
    (Apache + MySQL). No Composer packages are used - everything is native.

Q3. What is the folder structure?
A3. config/ (db.php - database connection, esewa.php - payment config),
    includes/ (header.php and footer.php shared across pages), admin/
    (dashboard, products, orders management), plus root-level pages:
    index.php (catalog), product.php, cart.php, checkout.php,
    order-success.php, failure.php, my-orders.php, profile.php,
    login.php, register.php, logout.php. model_store.sql is the complete
    database dump. assets/ holds CSS, JS, images and the logo.

Q4. How is the website structured (client-server flow)?
A4. It is a classic server-rendered PHP application. Every request goes
    to Apache, PHP executes the script, runs SQL queries against MySQL,
    and generates an HTML page that is sent back to the browser. JavaScript
    (assets/js/app.js) only enhances the experience (AJAX add-to-cart,
    theme toggle, lightbox, cart selection) on top of that HTML.

---------------------------------------------------------------------------
PART B - DATABASE
---------------------------------------------------------------------------
Q5. How many tables are there and what do they store?
A5. Five tables (model_store.sql):
     - users       : customer/admin accounts (full_name, email, bcrypt
                     password hash, role).
     - categories  : product categories (name, unique slug).
     - products    : product details (title, description, price, stock,
                     scale, type, image_url, FK category_id).
     - orders      : order header (customer info, shipping address, total,
                     payment_method, payment_status, fulfillment status,
                     transaction_uuid, esewa_ref_id).
     - order_items : the products inside an order (order_id, product_id,
                     quantity, unit_price) - a many-to-many link table.

Q6. What are the relationships between the tables?
A6. - products.category_id  -> categories.id        (one-to-many)
     - orders.user_id       -> users.id             (nullable, ON DELETE SET NULL)
     - order_items.order_id -> orders.id            (ON DELETE CASCADE)
     - order_items.product_id -> products.id        (ON DELETE CASCADE)
    order_items is the classic "junction/line-items" table that lets one
    order hold many products while keeping product data normalized.

Q7. Why is order_items a separate table instead of storing a list in orders?
A7. Normalization. It avoids repeating product data, lets each order hold
    multiple products with their own quantity and locked-in unit price, and
    makes aggregation (item counts, revenue) simple with JOINs and COUNT().

Q8. Why is product price duplicated in order_items (unit_price)?
A8. To snapshot the price at the time of purchase. If the admin later
    changes a product's price, past orders still show what the customer
    actually paid.

Q9. What primary key / auto-increment setup is used?
A9. Each table has an auto-increment 'id' primary key. The code retrieves
    the newly created order id with $pdo->lastInsertId() in checkout.php.

Q10. What is transaction_uuid and why is it unique?
A10. It is a unique order reference generated as "ORD-{order_id}-{time()}".
    It has a UNIQUE constraint in the database and is sent to eSewa as the
    transaction identifier. Because it is unique, the payment callback can
    reliably find the exact order.

---------------------------------------------------------------------------
PART C - DATABASE CONNECTION (config/db.php)
---------------------------------------------------------------------------
Q11. How does the site connect to the database?
A11. Through one shared file, config/db.php, included on every page with
     require_once 'config/db.php'. It creates a single PDO connection
     object ($pdo) using:
       host=localhost, dbname=model_store, username=root, password=""
     (standard XAMPP defaults).

Q12. Why PDO and not mysqli?
A12. PDO provides prepared statements that protect against SQL injection,
     consistent exception-based error handling, and a unified API. Setting
     PDO::ATTR_EMULATE_PREPARES => false forces MySQL to use real
     server-side prepared statements so user input is never concatenated
     into SQL.

Q13. What PDO options are set and why?
A13. - ATTR_ERRMODE => ERRMODE_EXCEPTION : SQL errors throw exceptions,
       making debugging and rollback easy.
     - ATTR_DEFAULT_FETCH_MODE => FETCH_ASSOC : rows return as associative
       arrays ($row['title']).
     - ATTR_EMULATE_PREPARES => false : real prepared statements.

Q14. How is the connection error handled?
A14. The connection is wrapped in a try/catch. If PDOException is thrown,
     the script dies with "Database Connection Failed: ...".

Q15. What is format_price()?
A15. A global helper in db.php that formats numbers as Nepali Rupees with
     two decimals, e.g. format_price(2399) returns "Rs. 2,399.00". It is
     used on every page that displays money so pricing format stays
     consistent.

Q16. What query methods are used in the project?
A16. $pdo->query() for parameter-less queries, $pdo->prepare() +
     execute() for queries with user input, fetch() / fetchAll() /
     fetchColumn() for reading, and lastInsertId() for new ids.
     Transactions via beginTransaction()/commit()/rollBack() are used in
     checkout.php so an order + its items + stock update are atomic.

---------------------------------------------------------------------------
PART D - AUTHENTICATION & SECURITY
---------------------------------------------------------------------------
Q17. How is registration implemented?
A17. register.php takes full_name, email, and password, sanitizes the
     email with FILTER_SANITIZE_EMAIL, hashes the password with
     password_hash($pass, PASSWORD_BCRYPT), and inserts the user. A
     duplicate email throws a PDOException which is caught and shown as
     "Email address is already registered."

Q18. How is login implemented?
A18. login.php looks up the user by email, then uses password_verify() to
     check the submitted password against the stored bcrypt hash. On
     success it stores user_id, full_name, and role in the session, and
     redirects admins to admin/dashboard.php.

Q19. Why is the password hashed and not stored in plain text?
A19. Security. bcrypt (via password_hash) is a one-way, salted hash. Even
     if the database leaks, the passwords cannot be read. password_verify()
     checks the hash safely without revealing timing differences.

Q20. How is logout implemented?
A20. logout.php clears $_SESSION, expires the session cookie, calls
     session_destroy(), then redirects to login.php.

Q21. How does the site know a user is an admin?
A21. At login, $_SESSION['role'] is stored. Every admin page starts with:
     if (!isset($_SESSION['user_id']) || $_SESSION['role'] !== 'admin')
     redirect to login. So an unauthenticated or non-admin user can never
     reach the admin panel.

Q22. What security measures are in place?
A22. - PDO prepared statements everywhere (blocks SQL injection).
     - htmlspecialchars() on all output (blocks XSS).
     - password_hash/password_verify for passwords.
     - Session-based auth checks on protected pages.
     - HMAC signature verification on the eSewa callback so payments
       cannot be forged.
     - A whitelist regex on the login 'redirect' parameter to prevent
       open-redirect attacks.
     - Stock availability check inside a transaction at checkout.

Q23. Are there any security weaknesses you know of?
A23. Yes, and it shows honesty/depth to mention them:
     - No CSRF tokens on the POST forms (login, checkout, admin status
       updates).
     - The eSewa secret key is hard-coded in PHP (config/esewa.php and
       checkout.php) - in production it should live in environment
       variables.
     - No rate limiting on the login form (brute-force protection).

---------------------------------------------------------------------------
PART E - CATALOG, SEARCH, FILTERS (index.php / product.php)
---------------------------------------------------------------------------
Q24. How does the catalog page work?
A24. index.php reads GET parameters: q (search), scale, category, and
     page. It builds a dynamic SQL query starting with "FROM products
     LEFT JOIN categories WHERE 1=1" and appends conditions for each
     filter using prepared statements. It runs a COUNT(*) query to compute
     total pages, then a LIMIT/OFFSET query to fetch only the current page
     (6 products per page).

Q25. How is pagination implemented?
A25. $per_page=6; the page number is taken from ?page= with a max(1,...)
     guard, total pages = ceil(total/per_page), and the SQL uses
     "LIMIT 6 OFFSET (page-1)*6". Pagination links preserve the existing
     search/filter query strings using http_build_query().

Q26. What are the search and filter criteria?
A26. - q (search): matches product title OR description with LIKE '%term%'.
     - scale: exact match on p.scale (1:18, 1:43, 1:64).
     - category: matches the category's unique slug.

Q27. How does product.php work?
A27. It validates the ?id GET parameter, fetches the product joined with
     its category name, and if not found redirects to the catalog. It shows
     the image, title, scale, type, price, description, and live stock
     status. "Add to Cart" posts to cart.php; "Buy Now" goes directly to
     checkout.php?id=... for a single-product direct checkout.

---------------------------------------------------------------------------
PART F - SHOPPING CART
---------------------------------------------------------------------------
Q28. How is the cart stored?
A28. Entirely in the PHP session as $_SESSION['cart'] - an associative
     array keyed by product id. No database table is needed. Because it is
     server-side, it survives across page loads but is lost when the
     session ends.

Q29. What actions does cart.php support?
A29. Three POST actions:
     - add    : validates the product, adds it (or increments quantity if
                it already exists). Supports AJAX via X-Requested-With
                header, returning JSON {success, cart_count}.
     - update : sets the quantity for a product.
     - remove : removes a product from the cart.
     It also calculates grand_total and total item count for display.

Q30. How does the "Add to Cart" button work on the homepage?
A30. The form has a data-ajax-add attribute. app.js intercepts the submit,
     sends a fetch POST with the X-Requested-With header, and on success
     shows a toast and updates the cart badge count without reloading the
     page. On the product page the same form posts normally.

Q31. How is the cart count shown in the navbar?
A31. header.php sums the quantities in $_SESSION['cart'] and renders a
     badge on the cart icon.

Q32. How does the "select items to checkout" feature work?
A32. Each cart row has a checkbox and the header has a select-all checkbox.
     app.js (initCartSelection) toggles hidden "ids[]" inputs inside the
     checkout form (disabled = not submitted). The checkout button label
     shows how many items are selected and it blocks submission if nothing
     is selected. checkout.php then reads the ids[] array and only checks
     out those items. Selecting all the items is effectively the old
     whole-cart behaviour.

---------------------------------------------------------------------------
PART G - CHECKOUT & ORDER CREATION
---------------------------------------------------------------------------
Q33. What happens at checkout.php?
A33. 1. It requires the user to be logged in (redirects to login.php with a
        redirect= parameter so they return after login).
     2. Builds the list of items to buy - either from the selected ids[],
        or a single product (?id= from "Buy Now"), or the whole cart.
     3. Shows a shipping form (full name, phone, city, address) plus a
        payment method choice: eSewa or Cash on Delivery.
     4. On submit, inside a database transaction it inserts the order,
        stores the unique transaction_uuid, inserts each item into
        order_items, checks stock and decrements it, then commits.

Q34. Why is a database transaction used?
A34. So order + items + stock update are all-or-nothing. If any INSERT
     fails, rollBack() undoes everything and no half-order is left behind.

Q35. What happens after the order is saved (for each payment method)?
A35. - eSewa : the page builds the HMAC signature and renders a hidden
       auto-submitting form to eSewa's payment URL (a loading spinner is
       shown meanwhile).
     - Cash on Delivery : redirects to order-success.php with the
       transaction_uuid and status=cod.

Q36. How is stock decremented and protected?
A36. Inside the same transaction, each product's current stock is read
     with "SELECT stock ... FOR UPDATE" (row lock), and if stock is less
     than the requested quantity an exception is thrown (rolling back the
     whole order). Otherwise stock is reduced by the quantity. If the
     eSewa payment later fails/cancels, failure.php restores the stock.

PART H - ESEWA PAYMENT INTEGRATION (IMPORTANT - likely examiner focus)
---------------------------------------------------------------------------
Q37. What is eSewa and why is it used here?
A37. eSewa is the most widely used digital wallet in Nepal. Integrating it
     lets customers pay online instead of only cash on delivery. This
     project uses eSewa v2.0 in SANDBOX (test) mode - no real money moves.

Q38. What sandbox credentials are used?
A38. Product/merchant code: EPAYTEST, secret key: 8gBm/:&EnhH.1/q, and the
     payment URL: https://rc-epay.esewa.com.np/api/epay/main/v2/form
     (config/esewa.php and checkout.php).

Q39. Explain the complete eSewa flow.
A39. 1. Customer fills shipping details in checkout.php and clicks the
        button. The order is created in the DB with payment_status
        'pending'.
      2. PHP builds a signature and auto-submits a hidden HTML form to
        eSewa (fields: amount, total_amount, transaction_uuid,
        product_code, charges, success_url, failure_url, signature...).
      3. Customer pays on eSewa's hosted page.
      4. eSewa redirects the browser back to success_url with a base64
        'data' query parameter (on success) or failure_url (on fail).
      5. order-success.php decodes it, verifies the HMAC signature, and if
        valid marks the order payment_status='completed',
        status='Processing', and stores the eSewa reference.
      6. failure.php marks the order failed and restores stock.

Q40. How is the signature generated (this is the technical heart)?
A40. eSewa requires a base64 HMAC-SHA256 signature. The exact string is:
       "total_amount={total_amount},transaction_uuid={transaction_uuid},product_code={product_code}"
     signed with the secret key:
       hash_hmac('sha256', $data_to_hash, $secret_key, true)
     then base64_encode(). The fields must be in EXACTLY this order and
     the amounts must be plain strings. signed_field_names tells eSewa
     which fields were signed.

Q41. How is the callback verified (so fake payments are impossible)?
A41. order-success.php:
     1. base64_decode($_GET['data']) then json_decode.
     2. Check status === 'COMPLETE'.
     3. Rebuild the payload from the returned signed_field_names, in the
        same "field=value,field=value" format.
     4. Recompute hash_hmac('sha256', ...) -> base64 and compare with the
        returned 'signature'.
     5. If they match, the callback genuinely came from eSewa, so the
        order is marked paid. If not, the page shows "Signature mismatch"
        and the order is NOT marked paid - stopping someone from faking a
        payment just by visiting the URL.

Q42. What is base64 'data' in the callback?
A42. eSewa encodes its response as base64 JSON in a 'data' query
     parameter. It contains status, total_amount, transaction_uuid,
     transaction_code, product_code, signed_field_names, and signature.

Q43. Why both success.php and order-success.php exist?
A43. success.php is an older, simpler handler that marks the order
     completed but does NOT verify the signature. order-success.php is the
     real, secure page used by checkout.php - it verifies the signature.
     config/esewa.php still points to the old success.php URLs but
     checkout.php hardcodes the correct model_store URLs.

Q44. What happens on a failed/cancelled eSewa payment?
A44. eSewa redirects to failure.php with the same 'data' parameter.
     failure.php looks up the order by transaction_uuid, restores the
     product stock that was decremented at order creation, then marks
     payment_status='failed'. The customer can retry.

Q45. What would you change to go live with real payments?
A45. Replace EPAYTEST and the secret key with production merchant
     credentials, use the production payment URL, and update the
     success/failure URLs to the real domain (currently hardcoded to
     http://localhost/model_store/...). Move the secret out of the PHP
     files into environment variables.

PART I - ORDER HISTORY & PROFILE
---------------------------------------------------------------------------
Q46. How does my-orders.php work?
A46. It requires login. With ?view=<order_id> it shows one order's detail
     (only if it belongs to the logged-in user), otherwise it lists all of
     the user's orders with item counts (COUNT of order_items) and status
     badges. Details include items, subtotal, free shipping, payment
     status (Pending/Paid/Failed), and total.

Q47. How does profile.php work?
A47. It requires login, fetches the current user from the database by
     session user_id, and displays an avatar (first initial), name, role
     badge, email, role, and member-since date, plus My Orders and Sign
     Out buttons. It was added recently so the user-name button in the
     navbar opens the profile instead of jumping straight to orders.

---------------------------------------------------------------------------
PART J - ADMIN PANEL
---------------------------------------------------------------------------
Q48. What can the admin do?
A48. dashboard.php shows revenue (SUM of total_amount for non-cancelled
     orders), order count, product count, and the 5 most recent orders.
     products.php adds, edits, deletes, and lists products with an image
     picker (local assets) or external URL. orders.php lists all orders
     and lets the admin change fulfillment status (Pending / Processing /
     Shipped / Completed / Cancelled).

Q49. How is product management implemented?
A49. products.php handles GET ?delete=<id> (delete), GET ?edit=<id> (load
     into the form), and POST (INSERT or UPDATE). Categories are loaded
     for a dropdown. Images can be chosen from the local assets/images
     folder (scanned with glob) or pasted as an external URL with a live
     JavaScript preview.

Q50. How is the order status updated?
A50. orders.php POSTs order_id + new status, but only accepts values from
     an allowed whitelist ['Pending','Processing','Shipped','Completed',
     'Cancelled'] before running the UPDATE - preventing arbitrary values.

Q51. Is there a known issue with add-product.php?
A51. Yes - it checks $_SESSION['user_role'] but login.php stores 'role',
     so its access check never passes and the page is effectively dead
     code. products.php is the page actually used for product management.

PART K - FRONTEND / UI
---------------------------------------------------------------------------
Q52. What does the shared header do?
A52. header.php is included on every page. It computes $base_path ('../'
     on admin pages, '' elsewhere) so links/CSS/JS work from the admin
     subfolder. It shows the brand logo (assets/logo/logo.png), theme
     toggle, search box, cart icon with item count, a categories dropdown,
     and the correct auth menu (Sign In/Register, or user profile
     button/Admin/My Orders/Sign Out).

Q53. What JavaScript features exist?
A53. - AJAX add-to-cart with toast notifications and cart badge updates.
     - Quantity stepper on cart items.
     - Theme toggle (dark/light saved to localStorage).
     - Product image lightbox (click to enlarge).
     - Cart item selection for checkout.
     - AJAX pagination on the catalog.
     - Scroll animations and mobile navigation.

Q54. How does the theme toggle persist?
A54. A small script at the top of every page reads localStorage for the
     saved 'theme' and sets data-theme on <html> before rendering,
     avoiding a flash. app.js toggles it on click and saves the choice.

Q55. How does the product image lightbox work?
A55. On product.php the image is wrapped in a button with data-image and
     data-title. app.js opens a fixed overlay showing the enlarged image
     with the product title as caption. It closes on the × button, clicking
     the backdrop, or pressing Escape, and locks page scrolling while open.

Q56. How is the new logo applied?
A56. includes/header.php now renders <img class="brand-img"
     src="assets/logo/logo.png"> inside the brand link instead of the old
     "J" letter badge + text, with border-radius applied. It uses $base_path
     so it works from the admin pages too.

PART L - FLOW QUESTIONS (explain end-to-end)
---------------------------------------------------------------------------
Q57. Walk through what happens when a customer buys a product with eSewa.
A57. 1. Customer clicks Add to Cart (product card / detail page).
     2. Cart stores the item in the session.
     3. Cart page: customer ticks the items and clicks "Proceed to
        Checkout", which submits only the selected ids to checkout.php.
     4. checkout.php requires login. The customer fills shipping details
        and chooses eSewa, then submits.
     5. A transaction inserts the order + order_items, generates the
        transaction_uuid, checks and decrements stock, then commits and
        clears the cart.
     6. A hidden form auto-submits to eSewa with the HMAC signature.
     7. Customer pays on eSewa's sandbox page.
     8. eSewa returns to order-success.php with base64 'data'. The
        signature is verified, the order is marked completed, and the
        confirmation with purchased items is shown.
     9. The order also appears in my-orders.php (customer) and
        admin/orders.php (admin).

Q58. Walk through the Cash on Delivery path.
A58. Identical to eSewa up to step 5, but after commit the code redirects
     straight to order-success.php?transaction_uuid=...&status=cod, which
     loads the order and shows the success page. The payment_status stays
     'pending' because payment happens later on delivery.

Q59. How would you demo the project quickly?
A59. Start Apache + MySQL in XAMPP, open
     http://localhost/model_store/, browse the catalog, search/filter,
     open a product and click the image to open the lightbox, add items to
     the cart, select specific items, check out with a test account, and
     complete the eSewa sandbox payment. Then show admin/dashboard.php with
     the admin account to demonstrate order status management.

PART M - LIKELY "IMPROVEMENT / WHAT IF" QUESTIONS
---------------------------------------------------------------------------
Q60. What would you improve or add next?
A60. - CSRF tokens on all forms.
     - Move the eSewa secret key into environment variables.
     - Add email order confirmation.
     - Add stock input validation at add-to-cart time.
     - Product search with category dropdown in navbar search.
     - Admin dashboard charts (weekly sales).
     - Password change / account settings on the profile page.
     - Rate limiting on login.

Q61. Why didn't you use a framework like Laravel?
A61. This is a learning project built to demonstrate core PHP skills
     (sessions, PDO, prepared statements, transactions, HMAC signing,
     HTML/CSS/JS). Plain PHP shows a deeper understanding of how things
     work under the hood. The structure (config/, includes/, admin/) is
     already organised so it could be refactored into Laravel later.

Q62. What happens if two users buy the last item at the same time?
A62. The stock is checked with "SELECT ... FOR UPDATE" inside a database
     transaction, which locks the product row. Only one transaction can
     update it at a time, so the second user's check fails and they get an
     "Insufficient stock" message - preventing overselling.

Q63. How is the site protected against common attacks?
A63. SQL injection (prepared statements), XSS (htmlspecialchars output
     escaping), broken authentication (bcrypt + session checks), and
     payment forgery (HMAC signature verification on the callback). As
     noted earlier, CSRF and brute-force protection are the known gaps.
